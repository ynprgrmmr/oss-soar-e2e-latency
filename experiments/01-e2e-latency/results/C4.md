## ⚠ D_detect の偏り（計測の不具合）

C4 の D_detect は約 2 s に集中した（stdev 278 ms。C1 は 695 ms）。検知経路は C1 と同じなので、条件の差ではない。

- 原因: target の Wazuh agent は journald を **2 s ごと**に読む（`logcollector.loop_timeout=2`）。
  C4 は 1 試験が短く試験間隔がほぼ一定になり、試験の開始が 2 s 周期の同じ位相に揃ってしまった
- 根拠: T0 を 2 s 周期の位相で見たときの集中度 R は **C4 = 0.86**（ほぼ固定）、**C1 = 0.24**（一様に近い）
- 影響: C4 の D_detect と D_e2e は「読み取り直後に起きた」最悪側に偏っている。
  検知より後の区間（D_dispatch・D_api・D_enforce）は影響を受けない
- 対処: `run_batch.sh` に試験前のランダム待ち（既定 0〜4 s）を追加した。C4 を再計測するまで、
  E2E の比較は「検知後」の区間で行う

## C1 との比較（検知後の区間、偏りの影響なし）

| | C1（Shuffle 経由） | C4（AR 直結） | 差 |
|---|---|---|---|
| 検知後 p50 | 3,937 ms | 188 ms | **−3,749 ms（約 21 分の 1）** |
| 検知後 p95 | 5,285 ms | 438 ms | −4,847 ms |
| D_dispatch p50 | 3,813 ms | 56 ms | −3,757 ms |

- **SOAR 層（integratord → Shuffle）のコストは中央値で約 3.7 s**。C1 の E2E 中央値 5.3 s の約 7 割
- D_api と D_enforce は C1 とほぼ同じ。CHR 側の性能は経路によらない
- D_api の二峰性（約 24 ms と約 280 ms）は C4 でも出た。Shuffle ではなく CHR 側か TLS 接続の要因とみられる
- 参考: C4 の偏りのない E2E は「C1 の D_detect 分布 + C4 の検知後」で中央値 約 1.1 s と見積もれる（推定値。再計測で確かめる）
