- 実施: 2026-11-24 06:26–07:06 UTC、バッチ `batch-C2-20261124T062638Z`、試験前ランダム待ち 0〜4 s
- 経路: C1 と同じ（Wazuh → Shuffle → CHR REST）。**遮断の仕組みだけ**を変えた
- CHR の変更（計測中のみ）: raw prerouting `SOAR-A` を無効化、filter forward `SOAR-B` を有効化。
  filter に「確立済み通信を許可」ルールは入れていない（オーナー方針）。conntrack 上 established 扱いの
  UDP プローブも forward chain で落ちる
- 計測後に復元: raw 有効・filter 無効。手動で遮断して 10 プローブ送り、カウンタ増分が **raw +10 / filter +0** になることを確認

## 所見

1. **raw drop と filter drop で遮断反映の速さ（D_enforce）は変わらない**（中央値 102 vs 105 ms、p = 0.098）。
   確立済み通信を許可するルールが無い構成では、conntrack の前か後かは遮断の速さに効かない
2. **D_enforce の約 100 ms は遮断方式によらない**（C1 / C2 / C4-jitter の 3 条件とも 102〜105 ms、ばらつき ±3〜4 ms）。
   raw と filter で共通の部分、つまり address-list の変更がデータプレーンに反映される側の固定的な遅れと考えられる（仮説）
3. E2E の差は検知と受け渡し（Wazuh・Shuffle）のばらつきの範囲内。C2 の D_dispatch がやや短い（−251 ms、p = 0.051）のは、
   遮断方式と無関係な時間帯や Shuffle 側の状態の差とみられる（多重比較を考えると有意とは言えない）
4. 実運用の注意: 「確立済み通信を許可」ルールを filter の先頭に置く一般的な構成では、filter drop は既存の通信を切れない。
   今回の結果はそのルールが無い前提での値
