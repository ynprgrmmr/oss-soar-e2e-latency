- ワークフロー `e2e-block-src-2step`: Webhook → `stamp`（Shuffle Tools / execute_python: T1_soar を記録し srcip・run_id を出力）

## C1 との計測方法の違い（重要）

| 項目 | C1 | C3 |
|---|---|---|
| T2 の取り方 | アクション内のコードで `time.time_ns()`（ns） | **Shuffle の `chr_put` 結果の `completed_at`（ms）で代替** |
| T2_req | コード内（ns） | `chr_put` の `started_at`（ms） |
| CHR への TLS | CA で検証 | **検証なし**（標準 HTTP アプリは CA を指定できず `verify=false` のみ） |

- C3 の「T1_soar → T2」には、2 つ目のアクションのスケジューリング待ちと HTTP アプリの実行が含まれる。
  C1 の D_api（REST 呼び出しのみ）とは中身が違うので、下の表では **soar_to_T2** と呼んで区別する
- T2 を ms の `completed_at` で代替しても D_enforce は C1 と同じ約 102 ms（p = 0.11）だった。
  `completed_at` は HTTP 応答を受けた時刻とほぼ一致しているとみられる

## 所見

1. **アクションを 1 つ増やすと、E2E が中央値で約 1.2 s 延びる**（p = 0.004）。増えたのはほぼすべてアクション間の待ち（中央値 1,141 ms）で、
   HTTP アプリでの CHR 呼び出し自体は約 52 ms（C1 のコード内呼び出し約 22 ms より約 30 ms 長い）
2. アクション間の待ちは 348〜1,932 ms に散らばる。C1 の内訳で見た「worker → アプリへの送信」の待ち（中央値 742 ms）と同じ性質で、
   **Shuffle ではアクション 1 つあたり約 1 s のスケジューリング待ちが積み上がる**と考えられる（仮説）
3. 最初のアクションまで（D_dispatch）と CHR 側（D_enforce）は C1 と差がない
4. 実務上の示唆: 遮断のように遅れが効くワークフローでは、アクション数を減らす（処理を 1 つの Python アクションにまとめる）ことが最も効く
