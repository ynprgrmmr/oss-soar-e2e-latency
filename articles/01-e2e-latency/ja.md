# アラートからパケット遮断まで ― OSS SOAR とプログラマブルルータの「遮断の速さ」を測る

> 計測日: 2026-11-24。各条件 30 回の試験。本文の数値はすべてリポジトリの
> `experiments/01-e2e-latency/results/` にある集計と、`raw/` の生データから再現できる。

## まとめ

- 攻撃イベントが起きてから、攻撃元のパケットが**実際に止まる**までの時間を、OCI の Always Free 環境で 5 条件 × 30 回測った
- 基準構成（Wazuh → Shuffle → MikroTik の REST API）は **中央値 5.3 秒、p95 7.8 秒**
- そのうち **約 7 割は SOAR の受け渡し**（Wazuh が Shuffle にアラートを渡し、Shuffle が最初のアクションを動かすまで）で、
  ルータ側（API 呼び出しと遮断の反映）は合わせて約 0.12 秒しかない
- SOAR を通さず、Wazuh の Active Response からルータを直接操作すると **中央値 1.7 秒**。30 回すべてが、SOAR 経由で最も速かった試験より速かった
- Shuffle のアクションを 1 つ増やすと約 1.1 秒の待ちが加わる。raw で落とすか filter で落とすかは関係なかった。
  無関係なアラートを毎秒 20 件流しても遅くならず、むしろ速くなった
- 計測の途中で、試験の開始タイミングが Wazuh agent の 2 秒周期と揃ってしまう「位相同期」に気づき、ランダム待ちで解消した

## 1. なぜ「遮断までの時間」なのか

SOAR（Security Orchestration, Automation and Response）の紹介では、「アラートを受けてワークフローが動いた」ところで話が終わることが多い。
しかし防御側にとって知りたいのは、**攻撃に気づいてから攻撃者の通信が実際に止まるまで、何秒かかるのか**だ。
ワークフローが成功していても、遮断がネットワークに反映されるまでの間、攻撃者は通信を続けられる。

REST API で操作できるルータ（いわゆるプログラマブルネットワーク）を使えば、SOAR から遮断点を直接制御できる。
本稿では、OSS の SIEM/XDR である Wazuh、OSS の SOAR である Shuffle、ソフトウェアルータの MikroTik Cloud Hosted Router（CHR）を組み合わせ、
攻撃イベントの発生から実パケットが止まるまでを区間ごとに測った。

## 2. 構成

> 図: OCI 上の構成（Mermaid 版は [`diagrams.md`](diagrams.md) §1、draw.io 版は [`diagrams/oci-topology.drawio`](diagrams/oci-topology.drawio)）

| VM | Shape | 役割 |
|---|---|---|
| soar | A1.Flex 3 OCPU / 18 GB（arm64） | Wazuh 4.14.10（manager・indexer・dashboard）と Shuffle 2.3.0 を同居 |
| chr | A1.Flex 1 OCPU / 6 GB（arm64） | MikroTik CHR 7.25.1。遮断点 |
| attacker | E2.1.Micro | 攻撃イベントの発生と計測（T0・T3） |
| target | E2.1.Micro | 被害側。sshd、Wazuh agent、UDP エコー |

すべて OCI の us-phoenix-1（このテナンシのホームリージョン）に置き、Always Free の範囲に収めた。

**target の通信を必ずルータ経由にする。** VCN を public（soar、CHR の WAN 側）、attacker、protected（target、プライベート）の 3 サブネットに分け、
OCI の intra-VCN ルーティングで次の経路を作った。

- attacker と public サブネットから protected 宛ての通信 → CHR の WAN 側 IP へ
- protected サブネットから外向きの通信（VCN 内の他サブネット宛てを含む） → CHR の LAN 側 IP へ

戻りの通信もより長いプレフィクスで CHR に向けるので、経路は対称になる。CHR の 2 枚の VNIC では送信元/宛先チェックを無効にしている。
こうすると、CHR の address-list `soar-blocklist` に攻撃元 IP を入れるだけで、その IP からの通信を止められる。
遮断は `raw/prerouting` で行う（C2 だけ `filter/forward`）。

## 3. 何をどう測ったか

> 図: T0〜T3 の計測フロー（Mermaid 版は [`diagrams.md`](diagrams.md) §2、draw.io 版は [`diagrams/e2e-sequence.drawio`](diagrams/e2e-sequence.drawio)）

| 時刻 | 意味 | 取得場所 |
|---|---|---|
| T0 | 攻撃イベントの発生（attacker が `soar-probe-<run_id>` という存在しないユーザで SSH 接続） | attacker |
| T1_detect | Wazuh がアラートを出した時刻（独自ルール 100510） | soar（`alerts.json`） |
| T1_soar | 応答側のコードが動き始めた時刻（Shuffle のアクション、C4 では Active Response のスクリプト） | soar |
| T2 | ルータの REST API が応答した時刻 | soar |
| T3 | パケットが止まった時刻 | attacker |

区間は次のように呼ぶ。

| 区間 | 式 |
|---|---|
| 検知 | T1_detect − T0 |
| 受け渡し | T1_soar − T1_detect |
| API | T2 − T1_soar |
| 遮断反映 | T3 − T2 |
| **E2E** | **T3 − T0** |

**T3 の決め方。** attacker から target へ 10 ms ごとに UDP プローブを送り、target がそのまま返す。
遮断されると返事が来なくなるので、「最後に連続して返事が来なくなった最初のプローブ」の送信時刻を T3 とした。誤差は ±10 ms。

**時計のずれ。** T0 と T3 は同じ attacker の時計で取るので、主な指標の E2E にはホスト間の時刻ずれが入らない。
区間ごとの値はホストをまたぐので、全 VM を chrony で OCI の NTP に同期した。試験の前後で記録したずれは 10〜150 µs で、
区間の大きさ（数十 ms〜数秒）に比べて無視できる。

**応答側のコード。** Shuffle のワークフローは、Python のアクション 1 つで「T1_soar を記録 → CHR の address-list に PUT → T2 を記録」まで行う。
アクションを分けると、アクション間の待ちが計測結果に混ざってしまうためだ（実際に混ざる量は C3 で測った）。
CHR への TLS は、ラボ用に作った CA で検証している。

## 4. 試験条件

| ID | 条件 |
|---|---|
| C1 | 基準: Wazuh → Shuffle（Python アクション 1 つ）→ CHR、raw drop |
| C2 | C1 の遮断を filter/forward drop に変更（確立済み通信を許可するルールは置かない） |
| C3 | C1 の Shuffle を 2 アクションに分割（Python で記録 → 標準の HTTP アプリで PUT） |
| C4 | Shuffle を通さず、Wazuh の Active Response（manager 上で実行）から直接 CHR へ |
| C5 | C1 に、ルール 100510 に一致しない無関係なアラートを毎秒 20 件加える |

各条件 30 回。1 回ごとに、前回の遮断が 60 秒で自動失効して通信が戻るのを待ってから次の試験を始めた。

### 落とし穴: 位相同期

最初に C4 を測ったとき、検知の時間が約 2 秒にきれいに揃ってしまった。検知の経路は C1 と同じなのに、C1 はばらついていた。

原因は、target の Wazuh agent が journald を **2 秒ごと**に読みに行く仕組み（`logcollector.loop_timeout=2`）だった。
C4 は 1 回の試験が短いので試験の間隔がほぼ一定になり、試験の開始がこの 2 秒周期の同じ位置に揃っていた。
その結果、毎回「読み取りの直後にイベントが起きる」最悪のタイミングになっていた。

![試験開始の位相](figures/fig4-phase.svg)

| 計測 | 位相の集中度 R | Rayleigh 検定の p | 判断 |
|---|---|---|---|
| 最初の C4（間隔が一定） | 0.86 | 3.4 × 10⁻¹³ | 2 秒周期に揃っていた |
| C4 の再計測（0〜4 秒のランダム待ち） | 0.11 | 0.71 | 一様と矛盾しない |

R は「試験開始が 2 秒周期のどの位置にあったか」を円周上に並べたときの偏りで、0 なら一様、1 なら完全に揃っている。
各試験の前に 0〜4 秒のランダム待ちを入れると偏りは消えた。C2・C3・C5 もランダム待ち付きで測り、R は 0.05〜0.14 だった。
C1 はランダム待ちなしで測ったが、もともと R = 0.24（p = 0.19）で偏りは見られなかったので、そのまま使っている。
**パイプラインに周期的な処理があるなら、試験の開始時刻はランダムにする必要がある。**

## 6. 考察

### 6.1 ボトルネックは SOAR の受け渡し

基準構成では、受け渡しが E2E の約 75% を占めた。どこで時間がかかっているかを、Wazuh のアラート時刻と、
Shuffle の backend・worker のログ（ns 単位のタイムスタンプ付き）から読み取った（設定は変えず、読み取りだけで調べた）。

| 内訳（C1） | 中央値 | 平均 |
|---|---|---|
| Wazuh 側: アラート → Shuffle の Webhook 受信 | 1,874 ms | 1,859 ms |
| Shuffle: Webhook → 実行の作成 | 66 ms | 180 ms |
| Shuffle: 実行の作成 → worker が拾う | 664 ms | 837 ms |
| Shuffle: worker → アプリのコンテナへ送る | 742 ms | 769 ms |
| Shuffle: アプリのコンテナ → コード開始 | 339 ms | 366 ms |

Wazuh 側の約 1.9 秒は、次の 2 つでほぼ説明できる。

- **integratord がアラートを拾うまでの待ち（0〜約 2 秒、中央値 約 0.8 秒）。** 一時ファイル名に残る時刻とアラート時刻の差が 0〜2 秒に均等に散らばっていた。
  一定間隔で `alerts.json` を読みに行く動きと考えられる
- **連携スクリプトの起動（約 0.6 秒）。** Wazuh 同梱の Python を起動して `requests` を import するだけで 0.6 秒かかる（soar 上で実測）

Shuffle 側の約 2.2 秒は、キューから worker が実行を拾うまでの待ちと、worker からアプリのコンテナへ渡すまでの待ちが大部分で、
どちらも数十 ms から 2 秒近くまで散らばる。定期的にキューを見に行く処理の待ちと考えている。

### 6.2 SOAR を通さないと 1.7 秒

C4（Active Response から直接 CHR）では、受け渡しが **54 ms（ばらつき ±2 ms）** まで縮んだ。
検知した後の時間（T3 − T1_detect）は C1 の 3,937 ms に対して 184 ms で、約 21 分の 1 だ。
E2E の分布は完全に分かれ、C4 で最も遅かった試験（3,088 ms）でも C1 で最も速かった試験（3,683 ms）より速かった
（Mann-Whitney U = 900、p = 2.9 × 10⁻¹¹）。

C4 の E2E の大部分は、agent の 2 秒周期の読み取りで決まる検知の時間だ。
検知の時間は C1 と差がなかった（p = 0.19）。経路が同じなので、これは想定どおりである。

C4 の Active Response スクリプトは、Wazuh 同梱の Python ではなく OS の python3 と標準ライブラリだけで書いた。
同梱の Python では起動だけで 0.6 秒かかり、「SOAR 層があるかないか」の比較がぼやけるためだ。

### 6.3 アクションを 1 つ増やすと約 1 秒

C3 は E2E が中央値で 1.24 秒長くなった（p = 0.004）。Shuffle の記録で内訳を見ると、増えた分のほぼすべてが
**1 つ目のアクションが終わってから 2 つ目が始まるまでの待ち（中央値 1,141 ms）**で、HTTP アプリで CHR を呼ぶ時間自体は約 52 ms だった。
6.1 で見た「worker からアプリへ渡すまでの待ち」と同じ性質のもので、Shuffle ではアクション 1 つごとに約 1 秒の待ちが積み上がると考えられる。

なお C3 では、T2 を Shuffle が記録する HTTP アクションの完了時刻（ms 単位）で代用した。また標準の HTTP アプリは CA を指定できないので、
CHR への TLS 検証を無効にしている。遮断反映（T3 − T2）は C1 と同じ約 102 ms だったので、この代用による大きなずれはないとみている。

### 6.4 raw と filter に差はない。約 100 ms はどの条件でも一定

C2（filter/forward drop）は、遮断反映が C1（raw）と変わらなかった（中央値 102 ms と 105 ms、p = 0.098）。
今回は filter に「確立済みの通信を許可する」ルールを置いていないので、すでに流れている UDP のプローブも forward chain で落ちる。
接続を追跡する前に落とすか後に落とすかは、この構成では速さに効かない。

一方、API の応答から実際にパケットが止まるまでの約 100 ms は、**C1〜C5 のすべてで 102〜105 ms とほぼ一定**だった（ばらつき ±3〜4 ms）。
raw と filter に共通する部分、つまり address-list の変更がパケット処理に反映されるまでの決まった遅れだと推定している（未検証）。

実運用では、filter の先頭に「確立済み通信を許可」ルールを置く構成がふつうだ。その場合、filter での drop は既存の接続を切れない。
今回の C2 の値は、そのルールが無い前提のものである。

### 6.5 背景アラートがあるとむしろ速い

C5 では、無関係なアラートを毎秒 20 件流した（agent の送信上限 500 件/秒に比べれば軽い負荷）。
E2E は遅くなるどころか、中央値で 0.66 秒短くなった（p = 0.018）。

![受け渡しの内訳 C1 と C5](figures/fig3-dispatch-breakdown.svg)

内訳を見ると、短くなったのは **Wazuh 側（アラート → Webhook）だけ**で、平均 1,859 ms から 1,227 ms になった。Shuffle 側はほとんど変わらない。
アラートが途切れなく届くと、integratord が新しいアラートを待つ時間が生じないためと考えられる。
6.1 で見た「拾うまでの待ち（中央値 約 0.8 秒）」と、縮んだ幅がほぼ一致する。
処理能力を使い切るような負荷ではないので、「この程度の背景アラートなら遅延は悪くならない」という結果として読むのが妥当だ。

## 7. 実務への示唆

- **数秒の差が効く場面なら、遮断は Active Response に置く。** SOAR で行う場合も、遮断までの処理は 1 つのアクションにまとめる
- **Wazuh → SOAR の受け渡しには 2 秒前後の待ちがある。** 連携スクリプトの起動時間と integratord の待ちは、設定や実装で縮められる余地がある
- **RouterOS では raw で落とすか、drop より前に確立済み通信を許可しない。** そうしないと既存の接続を切れない
- **遅延を測るときは、試験の開始時刻をランダムにする。** 経路上の周期的な処理と揃うと、結果が大きく偏る

## 8. 環境構築で引っかかった点

- **Terraform の依存循環。** ルートテーブルが CHR の Private IP の OCID を参照するので、サブネットを作ってから CHR を作り、あとでルートテーブルを付け替えた
- **CHR のカスタムイメージ。** QCOW2 に変換し、UEFI で起動する設定と A1.Flex で使える設定を入れる必要があった。2 枚目の NIC は一度再起動しないと認識されなかった
- **RouterOS の初期状態。** admin はパスワードなし。filter が空のときに `place-before=0` を付けるとエラーになる。REST API で `.id` の `*` を URL エンコードすると 400 が返る。無償ライセンスは 1 Mbit/s の制限がある（計測のプローブには影響しない）
- **OCI の Ubuntu のファイアウォール。** ホストの iptables が SSH 以外を拒否している。Docker が公開したポートはこの INPUT ルールを通らないので、DOCKER-USER で制限した。NIC の名前は A1 では `enp0s6` で、最初に `ens3` と決め打ちしてルールが効いていなかった
- **Docker 29 と Shuffle。** Docker 29 が標準で使う containerd の image store では、Shuffle がアプリのイメージを読み込めなかった。containerd snapshotter を無効にして解決した
- **Wazuh と Shuffle の同居。** どちらも OpenSearch を使い、9200 番がぶつかる。Shuffle 側の OpenSearch をホストに公開しない設定にした

## 9. コストと運用

- Always Free の範囲: A1 合計 4 OCPU / 24 GB、E2.1.Micro 2 台、ブートボリューム合計 200 GB。以前から残っていた不要な VM（ブートボリューム 47 GB）を 1 台削除して枠に収めた
- 月 ¥100 の Budget アラートと、lab コンパートメントの VM を毎晩止めるスケジュールを、実験とは別の Terraform state で管理した。実験を作り直しても安全網は残る
- クラウドへの変更はすべて「plan を提示 → 明示的な承認 → その plan だけを apply」の手順で行った

## 10. 制約

- 攻撃は 1 種類（存在しないユーザでの SSH ログイン）、リージョン 1 つ、ルータ 1 台、SOAR は 1 台構成
- 各条件 30 回。C1 だけランダム待ちなしで測った（位相の偏りは見られなかった）
- C3 の T2 は ms 単位で、CHR への TLS 検証を行っていない
- C5 の負荷は軽く、飽和する点はまだ見ていない
- 6.1 の integratord と Shuffle の待ちの仕組みは、ログからの推定でソースコードでは確かめていない

## 11. 次にやること

- 受け渡しの短縮: 連携スクリプトを OS の python3 + 標準ライブラリで書き直す、Shuffle（orborus）がキューを見に行く間隔を短くする
- 負荷を上げて、遅延が増え始める点を探す
- 遮断を解除するまでの時間、ルータが複数台ある場合
